## 2. 发布阻断项（按严重度）

### ① 共享端口的 512 个槽位能被空闲连接远程占死

**证据**：`python3 scripts/verify/slot_exhaustion.py`（会通过 —— 它证明的正是这个洞成立）。

判别器的并发上限是 `DefaultMaxConns = 512`（`internal/gateway/discriminator.go:222`），
所有隧道、所有动作共享。开 512 条 keep-alive 连接、每条发完一个请求就挂着不发，
就把它占满：此后**任何**新连接在信号量那一步被直接 `Close`，包括

- **ACME 挑战** → 证书首签/续签静默超时；
- 走 L2 降级的 agent → 连不上；
- 所有共享入口隧道 → 新连接被拒。

无需鉴权、无需真实负载。已经补了 `IdleTimeout`（默认 60s，`GatewayConfig.IdleTimeout`
可注入），但那**只压慢不解决** —— 55s 一次刷新即可续住，而且没有任何按源的账，
所以一台主机就能长期持有全部 512 个。

**该怎么修**（裁决已定，实现没做）：把单一全局池改成**按动作分预算**，
给 ACME 与承载（`carrier` ALPN）**预留**槽位，业务流量只能用剩下的那部分；
同时把容量做成可配置的。这样最坏情况从「证书签不出来 + agent 连不上」
退化成「业务连接被拒，而控制面照常」。

### ② `exposure=private` 谎报 `active`

`Validate` 放行这个枚举值，但数据面**一个监听器都不会建**，而
`cmd/nfrelay/runtime.go:992` 的 `refreshStates` 里没有对应的 case，
于是它落到初值 `StateActive` —— 控制台绿点、计入 TunnelsUp，客户端一律
connection refused。

**该怎么修**：在那个 switch 里加一条 `case t.Exposure == tunnel.ExposurePrivate`
报 `StateError` + 说明。**不要**在 `Validate` 里改成拒绝 —— `Validate` 跑在每一次
`PutTunnel` 上，加拒绝会让已经存在的这类隧道从此存不进去（同一条理由也适用于
`packets_per_second`，见 §3）。

控制台向导造不出这个组合，所以只有直接调 API 或声明式配置会踩到 ——
但那正是对接方会走的路。

### ③ 发布签名的公钥是占位的

`release/nomirelay-release.pub` 是占位密钥，**私钥不在任何人手里**
（`release/README.md` 自己说清了）。所以 `make verify` 与 `scripts/install.sh`
对任何真实发布产物**必然失败**。

**该怎么修**：在一台离线机上 `make keygen OUT=...`，把公钥换进 `release/`，
私钥留在那台机上（权限 600，永不进仓库），并把指纹publish到 README。
签名之所以是一道**独立**的门，前提就是私钥不在构建机上。

## 3. 应该做，但不阻断发布

按「用户会不会被误导」排序，不是按工作量。

- **`exposure=port` + `tls=gateway` 的 UI 谎报。** Validate 放行这个组合，
  独立监听器做的是纯裸 TCP 拼接（不握手、不解析一个字节），而控制台把端点渲染成
  `https://<中继IP>:<port>`，暴露面摘要显示「应用层鉴权已配置」。
  浏览器打开会 `ERR_SSL_PROTOCOL_ERROR`。最小修法：那个组合下把端点渲染成
  `tcp://` 并在摘要里点明 TLS 轴被忽略。
- **改 `max_conns` 会静默丢一分钟历史。** 重建 `exposure=port` 的入口监听器时
  快照读的是**新**监听器的 stats，于是仍在传数据的连接从「活跃会话」里消失、
  累计字节回到 0。（在飞连接本身**不**掉线 —— README 里那句「掐断在飞连接」
  已经改对了。）另两个已知后果：Close 与重新 Listen 之间有个短窗口新连接被 RST；
  旧连接持旧信号量，有效并发短时是「旧 + 新」。
- **TURN 的 `RelayedPacketsDown` 不存在。** `internal/turnsrv/turnsrv.go:45-47`
  有 `RelayedBytesUp/Down` 与 `RelayedPacketsUp`，独缺下行包数。
  同一块里那条「未查清的计量时序」**已经查清**（先系统调用后自增 + 读写在两个
  goroutine，是良性的可见性迟到，没有字节被漏计），所以 e2e 那条被放宽成
  「两个方向加起来非零」的断言现在**可以**收紧成「几百毫秒内轮询到上行非零」。
- **一个未裁决的 TURN 问题：`PublicIP` 是 IPv6 时该不该被接受。**
  `New()` 现在**接受**它，而服务器只绑 udp4/tcp4 —— 于是配置看起来生效、
  `iceServers` 照常发出去，IPv6-only / 464XLAT 的客户端连不上。
  这可能是「该在 `New` 里拒绝并说明」，也可能是「该真的绑 udp6」，我没有裁决。
  （原本有一个 `zz_probe_v6_test.go` 在探这件事，它随 92fd979 被误提交，
  现已删除 —— 它通篇是 `t.Logf` 加一个两种结果都通过的分支，
  锁不住任何不变量，留着只会让人以为这件事已经有结论。）
- **没有 `openapi.json`**。规格 §8.5 规定了 `make openapi` / `make api-diff` /
  `make gen-api-types` 与一个漂移门禁，三个目标都不存在。当前唯一的端点清单是
  `docs/integration/03-api.md` 与手写的 `web/src/api/client.ts` ——
  后者漂过（调过三个后端从未注册的端点）。
- **没有 Prometheus `/metrics`**。代码注释里以现在时提到 `nf_*` 指标名，
  而 `go.mod` 里没有 `prometheus/client_golang`。那些注释是意图，不是现状。
- **数据库没有恢复路径**。`store.Backup` 有实现、有测试、**零调用入口**。
- **SSE 忽略 `Last-Event-ID`**，断线重连静默丢事件（`sse.go:354` 的
  `var _ = lastEventID` 是那个解析函数唯一的引用）。
- **丢包率没有测量点**。`store.Sample.LossPPM` 只被写进 SQLite 再读出来，
  从没被赋过非零值。界面三处一律显示「—」而不是 0（0 会被读成「测过，是零」）。
- **首启窗口没保护**。`POST /api/setup` 未鉴权，谁先到谁是管理员。
- **浏览器覆盖只到 Firefox**。`scripts/browser-smoke.py` 抓出过四个类型检查
  抓不到的缺陷，但 Chrome / Safari / 移动端从未验证过。

## 4. 我替你做的裁决（**不要**当成 bug 顺手「修」）

这些是在你说「按全局技术架构最优方案裁决、不用问我」之后我定的。
每一条都有代价，代价也写在这里。

| 裁决 | 为什么 | 代价 |
|---|---|---|
| `packets_per_second` 在共享入口上**明确不生效** | 「包」这个概念在 TCP/HTTP 上不存在，能限的只是「每次 read」——那个语义没有用户能预期。名字对、语义走形比明确不生效更坏 | UDP 洪水防护只在 UDP 隧道上有 |
| 而且**不在 `Validate` 里报错** | `Validate` 跑在每一次 `PutTunnel` 上，加拒绝会让已经配过这个字段的既有隧道从此存不进去 —— 用更坏的故障修一个文案问题 | 用户可以配一个不生效的字段，只能靠 UI 与文档说清 |
| 共享入口的 `max_conns` 在 **HTTP 路径按在飞请求**算，**splice 路径按连接**算 | 共享入口上一条 keep-alive 连接可服务任意多请求、还能中途换 Host 换隧道，按连接算归属必然错 —— 本仓已因「连接级判断约束请求级路由」修过两个真实绕过。splice 路径隧道固定，所以那里语义与独立监听器一致 | 同一个字段在同一个端口上有两种语义，必须在文档里讲清（已讲） |
| 限额状态活在路由表**之外**（`Registry` 上一个 `ReplaceWith` 不碰的字段） | `applyShared` 每次 agent 上下线都重建路由表并对每条隧道 `Invalidate`。状态放进去 = 令牌桶每次抖动被清零，而桶初始是满的 → **拔网线就能拿到不受限带宽** | 多一个需要 `RetainLimits` 显式回收的生命周期 |
| 桶用 `atomic.Pointer` 挂在稳定对象上，包装**不捕获**它 | 否则一条长命连接（WebSocket、splice 出去的裸 TCP，能活几天）永远跑建立那一刻的速率 —— 而调低带宽的典型动机恰恰是压住**正在进行**的滥用 | 每次读写多一次原子加载 |
| splice 只在**读**侧结账（`throttleRead` 返回 `io.Reader`） | 包一条管道的两端会让同一批字节被同一个桶算两次，「配了 1 Mbps 只跑 500 kbps」也是谎。返回 `io.Reader` 让那个写法**根本写不出来** | —— |
| 改并发上限时**换对象**而不是原地改 | 信号量容量无法原地改 | 有效上限短时变成「旧 + 新」，有界且自愈（旧对象随最后一个 release 被 GC） |
| 向导里「中继直接拨号」**禁用而不隐藏** | 那条路径数据面不存在。隐藏会让人以为这一项不存在，然后去别处找；禁用 + 说明理由，他才知道是「还没做」 | 向导上多一个灰掉的选项 |
| 学习模式的观测**只在内存里**，重启即清 | 库会被备份、事件表会被支持包外发 —— 落库等于把「谁在什么时候连过这台中继」写进一份要发给别人的文件 | 重启后要重新攒，所以接口回 `observed_from`，界面必须显示它 |
| `:apply-learned` 收到**显式空数组**报 `nothing_selected` | Go 的 `[]string` 分不出「没传」和「传了空」，而 `{"cidrs":[]}` 曾经**应用了全部** —— 学习窗口里扫描器与真客户端混在一起，全选等于把攻击者写进 allow 表 | 请求体那个字段是 `*[]string` |
| 学习列表到顶（每隧道 256 条）**拒新而不挤旧** | 挤旧的话一次扫描会把运维真正在找的早期客户端全部冲走，而一份被截断的列表拿去收窄会**锁死没上榜的真实客户端** | 到顶后要清一次才能继续观测；`truncated` 必须报到界面 |
| L2 上 UDP 隧道报 `degraded` 而不是硬塞进可靠流 | frp 就是那样做的：用户以为拿到了低延迟通道，实际是 TCP over TCP | 那一级上 UDP 真的不可用 |
| 拒绝 RFC 6062 的 TURN TCP 分配 | pion 那条路径加了 `SO_REUSEADDR + SO_REUSEPORT`，而客户端能影响 `RequestedPort` → 两个客户端的分配共用同一个中继端口，入向连接被内核随机派 | 零真实能力损失（WebRTC 从不请求它） |
| 登录限速只有 per-IP，没有独立全局桶 | 真全局桶只要 1 个 IP + 2 次/分钟就能锁死所有人，比现状便宜四千倍 | 两条已如实写进 README：反代形态下 per-IP 事实上就是全局桶（约 3 次/分钟即可让管理员永久 429）；直接暴露形态下超过 4096 个 /64 后退化为共享溢出桶，而 `evictIdle` 只清满桶，攻击者造的空桶永不被清 |
| 不读 `X-Forwarded-For` | 数据面把 XFF/XFP 当不可配置的安全不变量在剥。控制台再立一个「信任这个头」的开关，仓库里就有两个互相矛盾的信任锚 | 反代形态下所有请求共用一个限速桶 |
| 共享入口只宣告 HTTP/1.1，不宣告 h2 | WebSocket 升级要 `ResponseWriter` 支持 Hijack，h2 的不支持，而 WS 穿透是核心场景 | 共享入口上没有 h2 |
| 没有 DNS-01，通配域名拿不到 ACME 证书 | 通配回落会让 `*.example.com` 下任意子域都成为可签发目标 —— 那正是被滥用的形状 | 转发不受影响，通配照旧生效 |
| 「中继自己拨号」不做 | 中继侧得先实现与 agent 同一套目标策略（默认拒绝 + 云元数据黑名单 + 每次拨号校验已解析地址），否则那条路上没有 SSRF 防线，一个被攻陷的控制台就是内网跳板 | v1 里所有隧道都必须有 agent |

## 5. 接手时最容易踩的四个坑

1. **真起进程验证之前先清残留。**
   `ps -eo pid,etime,args | grep -E "[n]frelay|[n]fagent"`。
   残留进程占着端口时你会连到一台**陈旧的**中继，症状与真实原因毫无关系。
   起子进程要**先 `go build` 再跑二进制** —— `go run` 的 SIGTERM 只到父进程。
2. **`go test -run X` 在零个测试匹配时也退出 0。** 用它做变异验证（改坏代码确认
   测试变红）时必须数 `=== RUN` 的条数，否则「没有测试跑」会被读成「测试通过」。
   我在这上面自己骗过自己一次。
3. **限速测试只断言下界。** `-race` + 真 TCP 下挂钟上界不可靠。速率取 ≥
   `minByteBurst`、载荷取 3 倍速率、断言耗时下界 + 字节数**精确相等**。
   「双重计费」这个失效形态测不出挂钟差异，所以用 `metered` 计数器做确定性断言。
4. **一次 `Read` 会把后面的载荷一起吞。** `internal/gateway/limits_test.go` 里那条
   1/3 概率的假失败就是这个：读 ClientHello 的那次 `Read` 顺带拿走了约 14 KiB 载荷，
   之后再要 `size` 个字节等于把已收到的那一截又等一遍，超时后报「字节少了」——
   看起来**像限速在丢数据**。按总量收才对。
