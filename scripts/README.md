# NomiRelay

**通用网络中继器**：把家庭/工厂内网里的 HTTP、WebSocket、TCP、UDP 服务，
经一台公网中继暴露给手机与 IoT 设备。

吸收 [frp](https://github.com/fatedier/frp) 的反向代理形态与
[EasyTier](https://github.com/EasyTier/EasyTier) 的中继信任模型，
并在三处做了结构性修正（见[为什么不直接用 frp](#为什么不直接用-frp)）。

- **接入文档**：[`docs/integration/`](docs/integration/) —— 面向外部团队，
  描述**代码当前的实际行为**（含 API 参考、线协议规范、真实能力矩阵、已知缺口）。
  与规格不一致时以它为准。
- **工作交接**：[`docs/HANDOVER.md`](docs/HANDOVER.md) —— 面向下一个动这个仓库的人：
  发布阻断项、待办分级、以及每一条「看起来像缺陷其实是裁决」的理由与代价。
- 设计规格：[`docs/superpowers/specs/2026-08-07-nomirelay-design.md`](docs/superpowers/specs/2026-08-07-nomirelay-design.md)（规范性文档）
- 调研档案：[`docs/research/`](docs/research/) —— 16 份实读 frp/EasyTier 源码得出的设计输入

## 目标场景

| | 场景 | 形态 |
|---|---|---|
| **S1** | 服务对接 | 公网手机 → 中继 → 家庭 NAT 后的桌面服务器，走 HTTP/WebSocket/UDP |
| **S2** | 反向代理 | 工厂机器人**只填中继 IP + 端口** → 指定远端桌面，设备侧零客户端软件 |

S2 的「只填 IP+端口」不是偏好而是设备能力上限：nomifun 的 ESP32 机器人只能用裸 IPv4
明文 http/ws，不做 SNI、不校验证书，配主机名会**启动失败**。

## 快速上手

```bash
make ui && make build   # 前端 + 两个二进制（合计约 25MB：nfrelay ≈18MB、nfagent ≈7MB，控制台已内嵌）
```

**1. 起中继：**

```bash
./bin/nfrelay -data-dir ./data
```

它会打印控制台地址与证书指纹：

```
  控制台：http://127.0.0.1:9443
  首次使用请打开控制台完成初始化（创建管理员）。

  承载地址：192.168.1.10:8443
  证书指纹：uAPK2wSCAnAGyP0YJnsNDzMhHeG6Xoh5WDDNdwv7wng=
```

**2. 打开控制台**完成初始化。首启向导的第三步「接一个目标」会签发一枚入网令牌
并给出一条**可直接复制**的入网命令：

```
nfagent -relay 192.168.1.10:8443 -pin uAPK2w… -token nf_enrol_6d1ece95…
```

之后想再要一条，去「代理端」页签发（API 是 `POST /api/enrol-tokens`，
字段 `install_cmd`，默认 15 分钟有效）。**建隧道向导里的「预览」给的是占位符命令**
（`-relay <中继地址> …`），只用于核对形状，不能直接跑。

**3. 在被暴露服务所在的机器上**贴上那条命令，等它上线。

**4. 回控制台建一条隧道。** 只有一个 agent 在线时新隧道会自动绑定它；
有两个及以上时中继不猜，隧道会报 error 并让你显式指定一个。

**5. 访问**——客户端完全不需要知道隧道的存在：

```bash
curl http://192.168.1.10:9090/api/hello
```

隧道存在 SQLite 里，**跨重启自动恢复**。

也可以纯 API 驱动（控制台就是它的消费者，没有隐藏接口）：

```bash
curl -X POST http://127.0.0.1:9443/api/tunnels \
  -H 'Content-Type: application/json' -H "X-NFR-CSRF: $CSRF" -H "Origin: $C" \
  -d '{"slug":"home-api","listen_port":9090,
       "backend":{"kind":"addr","addr":"127.0.0.1:8080"}}'
```

`-pin` 是中继证书的 SPKI 指纹。**本工具不提供「跳过证书校验」的选项**：
frp 在没配 CA 时默认 `InsecureSkipVerify=true`，让它宣传的「默认 TLS」只有加密没有认证，
MITM 门槛为零。这里宁可让你多贴一个指纹。指纹钉的是公钥而非整张证书，
所以证书续期不会打断绑定。

### 部署

```bash
docker compose up -d                      # 容器（distroless、非 root）
sudo install -m 0644 deploy/nfrelay.service /etc/systemd/system/   # systemd
```

**默认端口**：`8443/udp`（agent 承载）、`9443/tcp`（控制台，默认只绑 loopback）、
以及每条隧道各自的业务入口端口。最低可用集是这三者。

**控制台是明文 HTTP。** 默认只绑 loopback，所以流量不出机器 —— 那是正确的默认。
要远程访问，两种形态：

```bash
# 推荐：SSH 隧道，控制台仍然只绑 loopback
ssh -L 9443:127.0.0.1:9443 relay-host

# 或者：前面放一个做 TLS 终止的反代，并**显式声明**它
./bin/nfrelay -console 127.0.0.1:9443 -console-behind-tls-proxy               -console-hosts relay.example.com
```

`-console-behind-tls-proxy` 才会给会话 Cookie 加 `Secure` 与 `__Host-` 前缀。
它是一个**显式断言**而不是去猜 `X-Forwarded-Proto` —— 那是可伪造的请求头，
拿它做安全决策与本仓数据面的立场直接冲突（网关把 XFF/XFP 当不可配置的不变量在剥）。
反过来也要小心：声明了却其实没有 TLS，浏览器会因为 `Secure` 而**不保存 Cookie**，
现象是「登录返回 200、下一个请求 401」。设置页的 `console_session_hardening`
一项就是为诊断这个现象存在的。

`-console-hosts` 的条目**可以带端口**（`relay.example.com:9443`），两种写法都认。

## 为什么不直接用 frp

三处修正，全部由实读 frp v0.71.0 源码量化得出，不是审美偏好。

### 1. 新连接建立从 1.5×RTT 降到 0 额外 RTT

frp 开一条被代理连接要走 `ReqWorkConn` → `NewWorkConn` → `StartWorkConn` 三条控制消息
（`server/control.go:595-637`）。连接池能降到 0.5R，但客户端 `poolCount`
**默认只有 1**（`pkg/config/v1/client.go:153`），第 2 条并发连接就退化。
手机开一个网页 6 条并发连接，其中 5 条付满 1.5R——**这是 frp 首屏慢的根因，不是带宽问题**。

QUIC 与 smux 的流是**对称的**，服务端同样能开流。让中继主动开流并把隧道头与用户首包
一起 pipeline 出去，三条消息全部消失，连接池、`workConnPoolCapacityOffset`、
以及 `runID` 认领 workConn 的整套安全问题一并删除。

### 2. UDP 从「可靠有序流」改为「不可靠数据报」

frp 把全部 UDP 塞进**一条** TCP workConn（`server/proxy/udp.go:50-52`）。
UDP 本身不可靠无序——**语义错配才是队头阻塞的根因，调参调不掉**。
QUIC 不可靠数据报（RFC 9221）的语义与 UDP 逐条对应，是结构性修正而非优化。

同一路径上还修了三个缺陷：frp 的下行满队列会**阻塞**而非丢包
（`server/proxy/udp.go:140`，实时媒体必须丢弃）；NAT 会话表**无上限**且每个新源地址
开一个 socket（`pkg/proto/udp/udp.go:75`，从随机源端口喷包即可耗尽 fd）；
原始目的地址被丢弃（`:64` 传 nil，导致一条隧道无法承载多个 UDP 服务）。

### 3. 中继从「哑注册表」改为「权威存储」

frp 里**客户端**拥有代理配置，中继只是注册表——这正是它的中继控制台
**只有一个写操作**（`DELETE /api/proxies?status=offline`）的根因。
NomiRelay 让中继拥有 Tunnel 记录，但 agent 对**本地目标**保留一票否决：
否则一个被攻陷的控制台就是内网与云元数据的跳板。

## 当前状态

**已实现并验证**（`make check` + `make e2e` 全过）：

- **线协议**：12 字节帧头、能力协商、**未知类型跳过而非断连**的前向兼容（含 fuzz，千万级执行无崩溃）
- **握手鉴权**：HMAC-SHA256 + ±60s 时钟窗 + nonce 有界 LRU + **TLS exporter 信道绑定**
  （RFC 5705，label `EXPORTER-nomirelay-carrier-v1`，32 字节，混进 MAC 的 canonical）。
  绑定的作用是让一份被偷到的 Hello **搬不到另一条连接上**：e2e 里真跑了这次搬运，
  中继回 MAC 校验失败。首次入网那一跳不参与绑定（那时还没有密钥可签，
  令牌的防护是一次性作废）
- **承载梯级 L0 + L2 与自动回退**：L0 是 QUIC/UDP（首选），
  L2 是 **TLS/TCP:443 + smux**，突破「出口完全封锁 UDP」的网络 ——
  工厂与企业网常见只放行 TCP 80/443，而场景二的 agent 就装在那里。
  L2 与共享入口**共用 443/tcp**，靠 ALPN 区分（agent 协商 `nomifun-relay/1`，
  业务流量协商 `http/1.1`）；两个协议**分开两份 tls.Config**，
  因为宣告一个自己不会说的协议就是把握手成功的连接变成无法排查的失败。
  回退是**按梯级优先**而不是并发竞速：L2（TCP+TLS1.3）在近距离网络里常比 QUIC 快，
  竞速会让一台网络正常的中继上所有 agent 都跑在 L2 上 —— 而那一级**没有数据报**，
  UDP 隧道会静默全挂。所以给 L0 一段独占时间（1.5 秒）再试 L2。
  L2 上 UDP 隧道**如实报 degraded** 并说明「承载不支持不可靠数据报」——
  绝不把数据报塞进可靠流（frp 正是那样做的，得到的是调不掉的队头阻塞）。
  真机双向验证过：UDP 端口不可达时 agent 走 L2 且 TCP 隧道通流量、
  UDP 隧道报 degraded；UDP 正常时它留在 L0 且不打降级警告
- **QUIC 承载**：双向开流（0 额外 RTT）、RFC 9221 数据报、SPKI 指纹绑定、
  **反应式 MTU 学习**（quic-go 在一次 SendDatagram 超限时回
  `*quic.DatagramTooLargeError`，里面带着真实上限；分片器拿它决定分不分片）。
  这个值现在也进快照 —— 此前它只在承载层里影响转发，而界面那一格恒为「—」，
  于是一个**已经在生效**的机制看起来像没做。真机验证：发一个 60000 字节的
  UDP 报文之后快照从缺席变成 1404
- **隧道对象模型**：`kind × tls × exposure × l4` 四个正交枚举轴
  （frp 的 8 种代理类型收敛成四个可自由组合的维度）。**模型层正交，运行时还没完全兑现**：
  `exposure=private` 无实现、`exposure=port` 时 tls 轴被忽略（两条都在下面的诚实清单里）
- **SQLite 存储**：隧道/agent/令牌/事件持久化，RTT 存直方图桶（分位数不能被平均）。
  时序**只有 1 分钟表可查** —— 5m/1h 上卷表被写入与剪枝，但全仓没有任何读取点，
  所以历史查询实际只覆盖 1m 表的 48 小时留存（见诚实清单）
- **Web 控制台**：React 19 + Arco Design + UnoCSS + swr + uPlot，zh-CN 优先，embed 进单个二进制。
  首启引导、隧道 CRUD、双模式并排单选卡、实时 SSE、审计事件、暴露风险标记
- **网关模式与共享入口**（`-shared`，默认不启用）：共享端口惰性分级 peek、
  SNI 不解密即可路由、TLS 终止、Host/路径路由、请求头改写、
  未注册域名回真正的 `unrecognized_name` 告警而不是裸关闭。
  实测：HTTP 按 Host 路由 + Host 改写、WebSocket 101 升级与双向帧都通
- **agent 本地目标策略**：默认拒绝 + 云元数据永久黑名单 + **每次拨号校验已解析地址**（防 DNS 重绑定）
- **UDP 数据面（已接线，端到端可用）**：QUIC 不可靠数据报（RFC 9221）承载，
  会话表四重约束（容量上限 + LRU + 每源 IP 配额 + 建表限速）、按隧道短标识解复用、
  非阻塞发送器（quic-go 的 `SendDatagram` 队列满 32 条时会阻塞，
  直接在读循环里调它会冻结整条隧道所有流）、丢弃原因分标签计数
- **大报文分片与重组**（按隧道选）：批量隧道分片，实时隧道丢弃并计数
  —— 分片放大丢包影响，一帧迟到的音频等于丢了还白占带宽。
  重组器**五重**有界（并发数 + 字节总量 + 超时 + **单个数据报的分片条数** +
  **分片范围重叠即拒**）。分片条数那一条不是装饰：它是唯一挡住「稀疏 1 字节分片」
  那种 O(n²) 打法的界，而那种流量前三条界全都拦不住（实测约 279 KB/s 合法分片
  就能把解复用循环钉在 100% CPU，且是持着锁跑）。
  最后一条防的是 teardrop 那类「用重叠分片把内容藏过检查设备」；
  帧格式带数据报标识，否则同一条流上两个等长报文交错到达会被拼混
- **内置 TURN/STUN**（`pion/turn/v5`，默认不启用，需 `-turn-public-ip`）：
  对端地址过滤**默认拒绝**私有段与云元数据（pion 的默认 handler 放行一切，
  照抄示例得到的是一台通向本机私网的开放中继）、每分配的字节计量与分配明细
  （pion 既不暴露带宽计数器也没有枚举分配的 API，两者都靠包一层拿到）、
  全局配额、临时凭据与 coturn `use-auth-secret` 逐字节兼容、
  控制台一键签发可直接喂给 `RTCPeerConnection` 的 `iceServers`
- **ACME 自动签发**（`-acme`，默认不启用，默认 CA 是 **staging**）：
  共享入口与 `turns:` 共用同一个 `GetCertificate`。四道闸门是**必需**而非加固 ——
  核实过 certmagic v0.25.4：它内置的限速器是**排队器不是闸门**
  （`acmeclient.go` 调 `rl.Wait` 而非 `Allow`，粒度是 CA + 账户，
  于是一批未注册 SNI 会在 TLS 握手里**排队**而不是被拒），
  且**没有失败负缓存**（被 CA 拒掉的域名下次握手原样重试，
  而 failed-validation 限制比成功签发的更容易撞上）。
  另外 `SubjectQualifiesForPublicCert` **不**拒公网 IP 字面量
  （只调 `SubjectIsInternal`，对 IP 只判私有/回环）—— 而空 SNI 时
  certmagic 会拿**本地连接 IP** 当域名，所以 `SubjectIsIP` 必须显式调。
  自签证书作为回落**保留**：场景二的裸 IP 设备永远签不出证书，
  挤掉它等于让那些设备全线掉线。TLS-ALPN-01 作主路径（家宽常封 :80），
  `-acme-http` 是备份；两条路都没有时**启动即报错**，
  因为它的现象是签发静默超时
- **每隧道限额在两种 exposure 上都生效**（`policy` 的 `max_conns` /
  `max_conns_per_ip` / `bytes_per_second`）。此前只有 `exposure=port` 的独立
  监听器落实了它们，而共享入口（`-shared`）路径上零读取点 —— 用户给一条公网
  隧道配了 1 Mbps，界面确认「已设置」，它照样跑满。
  三条路径现在都接上了：网关（HTTP）按**请求**算并发、字节挂在隧道那一侧的
  连接上（一个挂点同时覆盖请求体、响应体、以及**升级之后的 WebSocket 双向
  字节** —— 少了最后一条，场景一的核心路径上限速会静默失效）；
  SNI 直通与明文兜底的 splice 按**连接**算，语义与独立监听器完全一致。
  限额状态活在路由表**之外**并且只在策略数字真的变了时才重建 ——
  `applyShared` 在每次 agent 上下线时都会整体替换路由表，跟着它清零就等于
  每次抖动都白送一份完整的突发额度（令牌桶初始是满的），
  也就是把限速变成一个可被外部驱动关掉的开关。
  真机验证：768 KiB 过 256 KiB/s 耗时 2.00 秒（不限速 0.00 秒），一个字节不少
- **每隧道限速**（`policy.bytes_per_second` / `packets_per_second`，令牌桶）：
  TCP 路径**等**（字节流丢中间一段就是把连接搞坏，反压自然传播到发送方窗口），
  UDP 路径**丢**并计数（等一秒的音频包到达时已经没有价值，而等的代价是占住
  共享读循环）。两个维度都要：10 万 pps 的 64 字节小包是现实攻击形态，
  任何按字节的限速器都会放行它
- **agent 侧计数器上报**（`TypeMetrics`，每 5 秒走控制流）：中继只看得见自己
  那一侧，而拨本地目标失败 / 被本地策略否决 / 回向发送队列满 / 回向超限 /
  回向分片重组失败这一整类它完全不知道。控制台把两侧**分开**显示 ——
  一边是中继观测的、一边是 agent 自报的，可信度与新鲜度不同，
  并标出「上报是不是卡住了」（一份十分钟前的数不该被当成现在的）
- **跨语言契约门禁**：事件种类枚举与接口契约版本在 Go 与 TypeScript 各写一遍，
  两条 Go 测试解析前端源码逐项比对。TS 那边 `kind` 的类型是
  `EventKind | string`，宽容到漂了也不报错 —— 而它确实漂过三种
- **每源 IP 配额**（`policy.max_conns_per_ip`）：TCP 与 UDP 两侧都有。
  只有全局上限时，一个源 IP 就能占满它并把别人挤出去 ——「最多 N 路」保护的是
  中继不被压垮，不是保护其他用户。配额大于全局上限时会被收敛
  （一个永远不触发的闸门比没有闸门更糟：用户以为自己配了保护），
  归零的表项立刻删除（键是源 IP、由任何能连上来的人指定）
- **PROXY protocol 信任开关**（`-shared-trust-proxy-protocol`，默认关）：
  打开时启动日志显著警告 —— 对不可信来源解析 PROXY 头等于把源 IP 伪造能力
  送给公网，那会让来源白名单、审计来源、每源配额同时失效。
  路由表全量重建时会重新设置它（不重设就会在第一次隧道变更时被静默关掉，
  于是前置 LB 后面的部署突然把所有客户端看成 LB 的地址）
- **`listen_port: 0` 由中继分配并回写**：那句注释一直承诺着这个行为而它没有实现。
  回写是必需的 —— 不回写则重启换端口，而 `exposure=port` 的客户端是拿端口号
  硬配的（场景二的设备写在固件里），换端口等于让所有客户端同时失联
- **承载 RTT 分位数**（控制流 Ping/Pong，5 秒一次）：p50/p95/p99 写进规格 §8.4
  要求的累积直方图桶（`tunnel_rtt_hist_1m`，`le_us`）——「p95 的 p95 在算术上
  是错的」，所以不存 p95 列。中继两次取时间戳、agent 的时钟完全不参与；
  序号用随机数而不是自增（自增可猜：预先灌一批 Pong 进控制流，
  读循环一瞬间落后就会把 RTT 报成接近 0）；只允许**一个**在飞的 ping
  （「序号→发出时刻」做成表就要想清楚清理，一个 slot 换掉一整类无界增长）；
  超时不算成一次观测（那会让一次丢包污染分位数）
- **活跃会话与累计会话分开**。之前控制台的「活跃会话」填的是累计接受数
  （只增不减），于是一条早就没人用的隧道会显示「活跃会话 1523」。
  规格 §8.4 要的是两项：活跃数回答「现在有多少人在用」，
  累计数差分出「新会话/秒」。UDP 侧本来报的是真活跃数，两侧原本还不一致
- **支持包下载**（`GET /api/diagnostics/support-bundle`）：一份**脱敏后的
  JSON 摘要**，含版本、schema 版本、生效配置及来源、隧道与 agent 摘要、
  近期 200 条事件、判别与网关计数、TURN 分配数、以及「哪几个可选接口装上了」。
  `store.Backup` **刻意不接**进这条路径 —— 库里有 agent 密钥的**明文**
  （HMAC 校验需要密钥本身）、argon2id 口令哈希、会话与 CSRF 令牌、
  入网令牌哈希、TURN 长期密钥，一份 DB 快照就是这台中继的完整沦陷，
  而支持包的用途恰恰是发给别人看。脱敏两道都要：键名白名单（secret/key/token…）
  加上对所有外发文本的形状匹配（`nf_enrol_*`、长十六进制串）——
  后者挡的是「将来某处 AppendEvent 不小心把令牌写进自由文本」。
  缺席的段落逐条说明**为什么**（空着不解释，读的人无法区分「没有」与「出错了」），
  下载动作留痕（它是一次外发，与签发 TURN 凭据同类），
  文件名里的版本串经过清洗（ldflags 可以是任意内容，
  一个带引号或换行的版本号会撕开响应头）
- **发布签名与一键安装**（`make sign` / `make verify` / `scripts/install.sh`）：
  Ed25519 detached 签名，私钥**只在离线机上**。用 openssl 而不是
  minisign / cosign —— 用户验签不需要装任何额外工具，而一个「要先装工具才能验」
  的签名多数人会直接跳过，那等于没有签名。（cosign 的 keyless 模式在本仓
  **不可用**：它依赖 CI 的 OIDC 身份，而组织铁律禁用 GitHub Actions。）
  安装脚本在**下载二进制之前**就验签，任何一步失败即中止且不留下已下载的文件；
  校验顺序是「先签名、再校验和」——反过来的话，一个替换了产物**并且**改了
  清单的发布会先通过校验和那一步
- **会话网格**（SSE `session` 帧，规格 §406）：裸端口 TCP 隧道的每条会话
  开/关都推一帧，带真实客户端地址、活跃数与累计数。地址**只推送、绝不落库** ——
  事件表会被支持包外发，而那是运行时观测到的第三方信息。
  每帧带上权威的活跃/累计值而不让前端自己累加：累加会在丢帧后**永久偏移**，
  而那种偏移不会自愈、也没有任何迹象说明它错了
- **声明式整份配置**（`POST /api/config:validate` / `:apply`，控制台「设置」页）：
  一份 `{"version":1,"tunnels":[…]}` 文档描述**期望的完整集合**，中继据此
  新建、更新、**删除**。两个端点而不是一个带 `dry_run` 标志的端点：
  「先看看会发生什么」与「去做」是两个动作，合成一个会让手滑漏掉一个参数
  变成一次真实的配置替换。`:validate` 是**真正的干跑**（一个字节都不写），
  回的 diff 里**逐条列出**将被新建/更新/删除的 slug —— 只回 `{"ok":true}`
  让用户在按下应用之前无从知道自己要删什么，而删除是这个操作唯一不可逆的部分。
  界面据此在真要删东西时弹一次确认并把 slug 列进文案里。
  更新**原地改**而不删了重建：短标识重新分配会让在途的 UDP 数据报串到别的隧道去。
  文档里的 `id` / `short_id` / `state` 一概不认 —— 前两个由中继分配
  （接受外来 ID 等于允许一份文档覆盖一条它没提到的隧道），
  第三个是运行时**观测**（接受它会让控制台把一条没在监听的隧道显示成「运行中」）。
  写入顺序是**先删再建**：一次「把 8080 从 a 换到 b」的导入若反过来，
  写 b 时 a 还占着那个端口，唯一约束会把一份完全合法的文档顶回来。
  一份被拒的文档**不给 diff**，只给逐条错误 —— 逐条校验跳过坏条目，
  拿剩下的算 diff 得到的是「合法的那一部分会做什么」，
  而那是中继永远不会进入的状态（真机验证抓出来的：一条 slug 拼错的文档
  回执里写着 `delete: ["web"]`，实际上它什么都不会做）
- **学习模式（一键收窄暴露面）**：中继把**实际观测到**的来源地址攒起来
  （裸端口 TCP 的会话、共享入口的每个请求、UDP 的每条新流，**只记被放行之后的**），
  界面在隧道详情页的「配置」页签里逐条列出命中次数与首见/最近，勾选后并入
  `allow_cidrs`。四条判据是这个功能能不能被信任的全部：
  **只在内存里、绝不落库**（第三方地址不该进备份与支持包）；
  **有界且截断可见**（到顶时拒新而不是挤掉最旧 —— 否则一次扫描会把运维真正在找的
  早期客户端全部冲走，而列表看起来还是满的；`truncated` 一路报到界面，
  因为一份残缺的列表拿去收窄会把没上榜的真实客户端全部锁死）；
  **与既有白名单取并集**（覆盖会把手填的网段悄悄删掉）；
  **空集合一律拒绝写入** —— `allow_cidrs` 为空的语义是放行一切，
  把空结果应用下去不是收窄而是保持全开，而界面会显示成功。
  一个**显式的**空数组同样被拒（`nothing_selected`）而不是当成「全选」：
  那个口子会让一个算出空选集的界面把撞门的扫描器一键请进允许列表
- 零停机重载、会话世代管理与顶替、部署物料（Dockerfile / compose / systemd）。
  优雅关闭**只排空控制台 HTTP**，业务连接被无条件关掉（见诚实清单）

**尚未实现**（诚实清单）：

- **共享入口上 `packets_per_second` 不生效**（另外三项已生效，见上）。
  它的设计目标是 UDP 小包洪水；在 TCP/HTTP 上「包」这个概念不存在，
  它能限的只是「每次 read」——那个语义没有任何用户能预期。与其做一个名字对、
  语义走形的版本，不如让它在这条路上明确不生效。**刻意不在校验层报错**：
  Validate 跑在每一次 PutTunnel 上，加一条拒绝会让已经配过这个字段的既有隧道
  从此存不进去 —— 那是用一个更坏的故障去修一个文案问题。
- **共享入口上 `max_conns` 的语义按路径分叉**：**HTTP 路径**（gateway / cleartext）
  上一个**在飞请求**算一个额度（升级后的 WebSocket 整段算一条）；
  而同一个端口的 **splice 路径**（`tls=passthrough` 的 SNI 路由、以及非 HTTP 的
  端口默认回落）仍然按**连接**算，与独立监听器完全一致。
  此前这一条笼统写成「共享入口按请求算」，于是给 `tls=passthrough` 隧道配
  `max_conns` 的人会以为自己配的是请求级额度，实际是连接级。
  差异是承载形态决定的：共享入口上一条连接可以服务任意多个请求、还可以中途
  换隧道（keep-alive 换 Host），按连接算的归属必然是错的 —— 本仓已经因为
  「连接级判断约束请求级路由」修过两个真实绕过。
  另外 `max_conns: 0` 在这条路上是「不设每隧道上限」，兜底的是共享端口自己的
  并发上限（`DefaultMaxConns` = 512）；独立监听器上 0 是「每隧道 512」。
- **共享端口的 512 个判别器槽位可以被远程占死，而 ACME 与 L2 承载与它共用。**
  **这是当前唯一的功能性发布阻断项。**

  判别器在 `Accept` 之后、`Decide` **之前**就占一个槽（`DefaultMaxConns` = 512），
  `Handle` 返回才还；而网关分支的 `Handle` 要等**连接关闭**才返回。
  真机实测：512 条「发完一个请求（哪怕 404）就挂着」的连接把整个共享端口占死 ——
  **无需鉴权、无需负载、也不需要配任何限速**。之后新连接被 RST、
  **ACME 挑战在信号量那一步就被关掉**（证书首签超时，或更糟：签成功、
  60 天后续签静默失败，届时全部 https 端点一起挂）、走 L2 降级的 agent 连不上。
  运维唯一的痕迹是 `shared.at_capacity`，而没人知道要看那一格。

  已经做的缓解：网关的 `http.Server` 补上了 `IdleTimeout`（此前 Go 会回落到
  `ReadTimeout`，两者都是 0 = **压根没有空闲超时**）。它回收**被遗弃**的连接，
  那是常见情形。但它**不关这个洞**：每 55 秒给每条连接发一个廉价请求就能一直
  占着，而端口级信号量上没有任何每源 IP 记账 —— 一台主机就够。

  真正的修法要三样：判别期用短命额度、判完按 action 换成对应类别的额度
  （给 ACME 与承载留位）、端口容量可配。`ActionCarrier` 让这条更紧：
  一个 L2 agent **整场会话**占一个槽，所以 N 个降级 agent 永久吃掉 N 个槽。
- **改 `max_conns` / `max_conns_per_ip` 时有一个短暂的「旧 + 新」窗口**：
  在飞的请求持着旧限额对象的额度，新请求用新对象，所以有效上限短时是两者之和。
  它有界且自愈（旧对象随最后一个 release 被回收）。带宽不受影响 —— 那一项是
  原地换桶，连对象都不换。
- **共享入口隧道仍然没有历史时序**，所以「我配的 1 Mbps 真的生效了吗」在界面上
  只能靠累计字节数自己做减法（采样循环只遍历 TCP 独立监听器，见下）。
  限速在 TCP 上表现为变慢而不是丢弃，所以也没有「被限了多少」的计数器。
- **改 `max_conns` / `max_conns_per_ip` 会重建 `exposure=port` 的入口监听器。**
  结论（带宽原地改、并发上限重建）是对的，但**「掐断在飞连接」是假的** ——
  `EntryListener.Close` 只 `close(done)` 与关监听 socket，而 `handle` 从不看
  `done`、两个 `io.Copy` 用的是运行时的 ctx，所以已建立的连接照常被代理下去。
  真实后果是另外三条：(a) Close 与重新 Listen 之间有一个**短窗口没人监听**，
  新连接被 RST；Listen 失败（端口被抢、fd 耗尽）则隧道落进 `entryErrors`
  并保持不通；(b) 旧连接仍持旧信号量、新连接用新信号量，有效并发短时是
  「旧 + 新」，时长由最长命的那条连接决定（工厂设备可以活几天）；
  (c) **计数器归零** —— 快照读的是新监听器的 stats，于是仍在传数据的连接
  从「活跃会话」里消失、累计字节回到 0，那一分钟的历史被静默丢掉。
- **`exposure=private` 是死枚举**：Validate 放行、零实现、状态谎报 `active`。
  控制台造不出来，只有 API 与声明式配置会踩到。
- **`exposure=port` 时 `tls` 轴被完全忽略**，而 UI 把端点渲染成 `https://`。
- **`packets_per_second` 在 TCP 上限的是「每次 read」而不是「包」** ——
  它的设计目标是 UDP 小包洪水，TCP 隧道上不要配。
- **UDP 与共享入口隧道没有历史时序**：采样只遍历 TCP 独立监听器。实时数字是对的，
  历史曲线永远空白。5m/1h 上卷表被写被剪枝但**全仓没有读取点**，
  所以 48 小时之外的数据一行也读不到。
- **`-drain` 只约束控制台 HTTP**，业务连接被无条件关掉；真实耗时取决于
  「有没有人开着控制台页面」（SSE 是长连接）。`GoAway` 帧定义齐全但零发送方。
- **向导里那个「中继直接拨号」选项已禁用**（此前它是可选的）。选中它会 patch 出
  `{kind: reverse, agent_id: ""}`，而那条路径在数据面不存在 —— 用户于是拿到一条
  永远停在「等待代理端上线」的隧道（对一个明确选了「不要 agent」的人，
  那是一句永远不会奏效的下一步），或者在恰好一个 agent 在线时被静默绑到那个
  agent 上，行为与所选相反。现在禁用并说明理由（禁用而不隐藏 —— 隐藏会让人
  以为这一项不存在，然后去别处找）。
- **`kind=reverse` 的「中继自己拨号」没有实现**，所以 v1 里**所有** kind 都必须
  有一个 agent 承载。三个入口（TCP、网关、UDP）都调 `SessionFor(t.AgentID)`，
  返回 false 就放弃，没有任何回落路径。未绑定 agent 的隧道会在恰好一个 agent
  在线时被自动绑上；在那之前状态如实报 `pending`。
  没做那条路径的主要原因是：中继侧必须自己实现与 agent 同一套目标策略
  （默认拒绝 + 云元数据黑名单 + 每次拨号校验已解析地址），否则 SSRF 防线
  在那里是缺失的 —— 而一个被攻陷的控制台就成了内网跳板。
  **这条此前是一个更坏的形态**：代码里有四处注释与判据断言那条路径存在，
  于是 reverse 隧道恒报 `active`（绿点），而每一个连接都被静默关掉。
- **登录限速是 per-IP 的，没有独立的全局桶**。反代形态下所有请求的源 IP 都是
  反代，于是那个桶事实上就是全局桶（这一形态下的降级是正确的：中继看到的确实
  只有一个客户端）。但**直接暴露**的形态下，「一千个 IP 各试一次」绕得过去。
  刻意不做全局桶：真全局桶只要 1 个 IP + 2 次/分钟就能锁死所有人，比现状便宜
  四千倍。但「per-IP 因此不是那个开关」这半个说法**不成立**，如实写清两点：
  ①**反代形态下 per-IP 事实上就是全局桶**，也就是说那个锁死管理员的开关在
  这一形态下已经存在 —— 任何能打到 `/api/login` 的人以约 3 次/分钟就能让管理员
  永久 429（进门即扣，不区分成功失败）。我们接受它，因为替代方案在直接暴露
  形态下同样自伤。②**直接暴露形态下也不是无上限的「一千个 IP 各试一次」**：
  超过 4096 个 /64 之后退化为共享溢出桶，而 `evictIdle` 只清「桶已满」的条目，
  所以攻击者造出的空桶永不被清 —— 那个溢出桶会牵连未被跟踪的管理员 IP。
  另一个已知弱化：成功登录会清掉该源 IP 的失败预算，所以反代后面与管理员同源的
  攻击者，会在管理员每次成功登录后拿到一份新的突发额度（量级：管理员一天登录
  5 次 = 攻击者多 50 次，而基线本来就有 2880 次/天）。
- **不读 `X-Forwarded-For`**，所以限速键在反代之后是反代的 IP。这是刻意的：
  数据面把 XFF/XFP 当作不可配置的安全不变量在剥，控制台再立一个「信任这个请求头」
  的开关，仓库里就会有两个互相矛盾的信任锚。
- **首启窗口没有保护**：`POST /api/setup` 未鉴权，谁先到谁是管理员。
  限速只是把尝试速率压住，挡不住「中继起来了但运维还没去初始化」这段窗口。
  规格 §8.2 原本规定了四条保护（生成密码写盘、非 loopback 拒绝启动等），
  v1 走的是另一条路，那次换向已如实记在规格里。
- **共享入口只说 HTTP/1.1，不宣告 h2**。网关刻意如此：WebSocket 升级需要
  ResponseWriter 支持 Hijack，而 h2 的不支持，而场景一要求 WebSocket 穿透。
- **「把共享端口整个交给一条隧道」刻意不提供配置**。
  `gateway.Registry.BindDedicated` 与判别第 0 步都在（规格 §7.3），
  而它们的正确配置表达是 `exposure: port` 的**独立监听器** ——
  那条路径仍然更强，但**理由变了**：限额三项现在共享入口上也生效了，
  剩下的差异是「7 个每隧道计数器」与「`tls` 轴的处理」。
  更要紧的是判别第 0 步**先于** ALPN `acme-tls/1` 那一步：在共享端口内部造一个
  独占旁路会静默吞掉 TLS-ALPN-01 挑战，而它「能成功绑定」的场合恰好是
  「这个端口上没有别的隧道」——也就是一台 `-acme -turn` 只服务单台设备的中继。
  现象是首签超时，或更糟：签成功、60 天后续签静默失败。
  另外冲突赢家会由 slug 字典序决定（`ListTunnels` 是 `ORDER BY slug`），
  于是改一条隧道的名字会改变另一条通不通。
  这一条曾经被实现，随后按上述三点回退，理由钉在 `BindDedicated` 的注释里。
- **声明式导入的写入不是原子的**（`config:apply`）。校验是一道**全量的门**：
  任何一条隧道不合法就整份拒绝、一个字节都不写。但通过校验之后的写入是逐条的
  （`internal/store` 没有跨多条隧道的事务口子），所以写到一半失败会留下
  部分应用的状态。那时回执是 `partial_apply` + `applied: N`（已生效几条），
  而**重跑同一份文档是安全的** —— 文档描述的是终态而不是增量。
  这一点如实写在回执文案里，不假装它是原子的。
- **限速在 TCP 上表现为变慢而不是丢弃**（字节流丢中间一段就是把连接搞坏），
  所以「超限速被丢弃」这一格**只在 UDP 隧道上渲染** —— TCP 隧道上它根本不显示，
  而不是显示成一个恒为 0 的数字。
- **不提供 RFC 6062 的 TCP 中继分配**（TURN）。pion 给那条路径加了
  SO_REUSEPORT（`relay_address_generator_static.go:87-91`，注释写着
  「let multiple connections bind to the same relay address」），
  而客户端能影响 RequestedPort —— 两个不同客户端的分配会共用同一个中继端口，
  入向连接被内核随机派给其中一个。WebRTC 从不请求它（浏览器的
  TURN-over-TCP 指的是**客户端腿**走 TCP，那与分配的传输协议无关），
  所以拒绝它不减少任何真实能力。
- **丢包率没有测量点**（`Sample.LossPPM` 只被写进 SQLite 再读出来，从没被赋过
  非零值）。界面上一律显示「—」而不是 0 —— 0 会被读成「测过，是零」。
  承载 RTT 与数据报 MTU **都已经有了**（后者见上）。
- **L1 与 L3 承载梯级未做**（L0/QUIC 与 L2/TLS443 都已交付，见上）。
  L1 是「QUIC 走 443」，它只在「放行 443/udp 但封了别的 UDP 端口」这种
  少见配置下才有用，而 L2 覆盖了更常见也更严格的「UDP 全封」。
  L3 是 WSS + smux，突破的是**敌视 ALPN** 的中间盒 —— 而 L2 恰好靠 ALPN
  区分承载与业务流量，所以那种网络里 L2 会被挡住。没做 L3 的代价是：
  一个会剥掉 ALPN 或只放行明文 HTTP 升级的代理后面，agent 仍然接不进来。
  `go.mod` 里还没有 `coder/websocket`。
- **TURN 只绑 udp4/tcp4，IPv6 中继未做**。pion v5.0.10 起，客户端省略
  `REQUESTED-ADDRESS-FAMILY` 时会跟随监听器的地址族，双栈监听会让省略该属性的
  浏览器拿到一个 IPv6 中继地址。要开 IPv6 得先有真实的 Chrome/Safari 可测。
- **通配域名拿不到 ACME 证书**。签发闸门只认**逐字**注册过的域名
  （`HasExactDomain` 而不是 `MatchHost`）：通配回落会让 `*.example.com` 下的
  任意子域都变成可签发目标，而那正好是被滥用的形状 —— 每个名字只算一次
  per-name 预算，可名字有无穷多个，于是全局预算在几十次握手里烧光。
  通配的正解是 DNS-01 + 一张通配证书，而 DNS-01 刻意没做
  （家庭/工厂部署多数没有 DNS API 权限，给了凭据又过期时现象会是
  「证书签不出来」而不是「DNS 认证失败」）。转发**不受影响**：`MatchHost`
  照旧跟着通配走。
- **会话网格只覆盖裸端口的 TCP 隧道**（`exposure: port`）。共享入口
  （`-shared`）的隧道网格仍然为空：HTTP 请求不是会话形状（一次请求一帧，
  且 keep-alive 下「会话」没有边界），而 WebSocket 的 101 只有开启点可观测 ——
  关闭点要包装被 Hijack 的连接才拿得到。只发开启帧等于批量制造永不消失的
  幽灵行，比不发更糟。UDP 也还没接（那需要在流的 admit/discard 上挂钩）。
- **会话网格没有历史、没有补发**。页面打开之前的会话看不到，刷新一次就清空。
  `Last-Event-ID` 被**完全忽略**：解析函数存在但没有任何调用点
  （一句 `var _ = lastEventID` 是它唯一的引用），既不读也不记日志，
  所以自动重连期间丢掉的帧是**静默**丢失。
  界面上那句「只显示本页打开之后观测到的会话」继续保留 ——
  它现在描述的是刷新语义，不再是「其实一帧都不发」。
- **会话帧是可牺牲的**：速率由外部输入（用户连接）决定，所以开启帧过一个
  20 帧/秒的令牌桶，队列满了就丢。一次端口扫描不该把控制台的共享队列冲垮、
  把 1Hz 的权威快照挤掉 —— 那时界面会停在旧数据上，而用户看到的是
  「一个正在被扫的中继看起来风平浪静」。关闭帧**不限流**（它的总量被已发出的
  开启帧封顶，而丢一个就是一条永不消失的幽灵行）。
- **无 `make gen-api-types` / `openapi.json` / `api-diff`**——前端类型是手写的，
  文件头注明「将来必须被生成版**替换**而不是并存」。
- **学习模式的观测只在内存里，重启即清空**（功能本身已交付，见上）。
  这些是运行时观测到的第三方地址，落库等于把「谁在什么时候连过这台中继」
  写进一份会被支持包外发的文件。接口回一个 `observed_from`，界面必须显示它 ——
  一份只攒了五分钟的列表看起来与攒了一周的一模一样。
  另一条固有局限：学习窗口里（`allow_cidrs` 为空、放行一切）扫描器与真客户端
  混在一起，中继分不开，所以界面不提供「一键全选」，只把命中次数与首见/最近
  摆出来让人自己勾。
- **承载 RTT 测的是「控制流往返」，不是拥塞控制器看到的链路 RTT。**
  Ping/Pong 走 QUIC 的**可靠**流，所以这个数含三样与网络无关的东西：
  丢包时的重传与队头阻塞、对端协程的调度延迟（MIPS 路由器上可达毫秒级）、
  两端的用户态处理时间。它偏大，且在丢包时会明显跳。
  拿链路 RTT 的路是 quic-go 的 `Config.Tracer` + `qlog.MetricsUpdated`
  （`MinRTT` / `SmoothedRTT` / `LatestRTT` / `RTTVariance` 都在里面，**已核实可行**）——
  没走那条是因为开 Tracer 会给每个发出的包加一次切片分配与接口装箱，
  且把 tracer 回调关联到 carrier 需要一张以对端 connID 为键、鉴权前就插入的表。
  这是一次**有意的取舍**，不是「测不到」。
- **承载 RTT 是会话级的**：同一个 agent 名下所有隧道显示**同一条**曲线。
  规格 §8.4 的「每隧道 RTT」是展示粒度，不是测量粒度 ——
  承载是每 agent 一条 QUIC 连接，那些隧道共享同一条链路。
- **那条 TURN 计量时序已经查清了，是一次良性的测试可观测性竞态。**
  `WriteTo` 与 `ReadFrom` 都是**先系统调用、后自增计数**，而 pion 的读循环
  与执行 `WriteTo` 的是**两个不同的 goroutine**。于是回环回声完全可以在
  上行那次 `Add` 执行之前就被读循环收到并计进下行 —— 观测到
  「下行非零、上行是 0」。**没有任何字节被漏计**，只是可见性迟到。
  据此该做的是把 e2e 断言从「两个方向加起来非零」收紧成「几百毫秒内轮询到
  上行非零」，逐方向的保证就回到 e2e 里了。同一块里还有一处不对称：
  有 `RelayedPacketsUp` 而没有 `RelayedPacketsDown`，下行包数没人计。
- **浏览器覆盖只到 Firefox（WebDriver）**。`scripts/browser-smoke.py` 会真实渲染
  八节（首屏挂载、中文与主题、走完首启表单、建一条隧道、逐页渲染、隧道详情页含学习模式面板、设置页的声明式配置编辑器、样式与可访问性），
  它抓出过四个类型检查抓不到的缺陷。但 Chrome / Safari / 移动端从未验证过，
  且冒烟只覆盖「渲染得出来」，不覆盖交互流程的完整性。
- **发布签名的流程已落地，但仓库里那把公钥是占位的**
  （`release/nomirelay-release.pub`）—— 它的私钥不在任何人手里
  （生成于临时目录，随构建环境消失）。正式发布前必须在离线机上
  `make keygen` 并替换公钥，见 `release/README.md`。
  流程本身端到端实测过：签名、验签、以及五条失败路径
  （篡改产物 / 篡改清单 / 缺签名文件 / 错公钥 / 清单外的文件）全都正确拒绝。
- 多中继/HA、IPv6 姿态定稿

**v1 明确非目标**：P2P 打洞（留了枚举位与接口缝）、L3/TUN overlay、
`bridge-protocol-v1` 兼容（与既有 `nomifun-bridge-server` 并存）、场景三远控。

## 开发

```bash
make help           # 列出全部目标
make check          # 提交前必过：fmt + vet + lint + test + 依赖约束断言
make e2e            # 端到端：真实 relay + agent + 后端服务跑在 loopback
make fuzz           # 协议解析器 fuzz（默认各 30s）
make ui             # 构建控制台前端到 web/dist
make web-check      # 前端类型检查与 lint
make dist           # 全平台交叉编译 + SHA256SUMS
make sign           # 离线签名（需 NFR_SIGN_KEY，只在签名机上跑）
make verify         # 校验一份发布（先验签名，再核校验和）
make keygen OUT=... # 生成一对发布签名密钥（在离线机上）
```

前端开发时 `cd web && bun run dev`（5173 端口，`/api` 代理到中继）。

`make check` 之外还有两组**不进门禁**的验证（太慢、要抢端口），
但上面那份诚实清单里若干条断言的证据就是它们跑出来的：

```bash
python3 scripts/verify/limits_e2e.py      # 共享入口限额真的生效；改带宽不重启就生效
python3 scripts/verify/slot_exhaustion.py # 共享端口 512 槽位能被空闲连接占死（阻断项证据）
python3 scripts/verify/l2_check.py        # 封 UDP 时 agent 自动退到 L2
python3 scripts/verify/learn_e2e.py       # 学习模式三端点 + 面板
python3 scripts/verify/mtu_check.py       # 数据报 MTU 反应式学习
python3 scripts/browser-smoke.py          # Firefox/WebDriver 真实渲染八节
```

跑之前**先清残留的 nfrelay/nfagent 进程**，否则会连到一台陈旧的中继，
症状与真实原因毫无关系。细节见 [`scripts/verify/README.md`](scripts/verify/README.md)。

**本仓刻意没有 GitHub Actions**（见 [AGENTS.md](AGENTS.md)）。门禁只有一个入口：
提交前本地跑 `make check`。

两个二进制的目标平台不同：`modernc.org/sqlite` 没有 MIPS 移植，所以 MIPS 路由器
只能构建 `nfagent`。`make check` 会用 `go list -deps` 断言 agent 代码不依赖存储层——
这正是出两个二进制而非一个带子命令的原因。
