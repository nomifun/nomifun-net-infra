# 发布签名公钥

`nomirelay-release.pub` 是校验发布产物用的 Ed25519 公钥。

## ⚠ 当前这把是**占位密钥**，不是真正的发布密钥

它是为了让签名流程能被端到端验证而生成的，**私钥不在任何人手里**
（生成于 `/tmp`，随构建环境消失）。

正式发布之前必须：

1. 在一台**离线机**上 `make keygen OUT=nomirelay-release`
2. 私钥 `nomirelay-release.pem` 留在那台机器上，权限 600，
   **绝不**拷到构建机、绝不提交进仓库、绝不放进任何 CI
3. 公钥 `nomirelay-release.pub` 覆盖本目录里这个文件并提交
   （顺带一层保险：仓库的 `.gitignore` 忽略 `*.pem`，所以即使私钥被误放进
   工作目录也不会被 `git add` 带进去 —— 但**不要**依赖它，私钥根本不该出现
   在这台机器上）
4. 把公钥指纹也写进 README 正文，这样用户能用两条独立路径核对它

## 为什么密钥必须离线

`make dist` 产出的 `SHA256SUMS` 是在**构建同一台机器**上算的，
所以它只防传输损坏、不防构建机被攻陷 —— 攻陷构建机的人可以同时改产物、
改校验和。签名是那道独立的门，而它只有在私钥不在构建机上时才成立。

规格 §13.1 还记了一条：**cosign 的 keyless 模式在本仓不可用** ——
它依赖 CI 提供的 OIDC 身份，而组织铁律禁用 GitHub Actions，没有那个身份来源。

## 为什么用 openssl 而不是 minisign / cosign

用户验签**不需要装任何额外工具** —— openssl 在几乎所有 Linux / macOS 上都在。
一个「要先装工具才能验」的签名，多数用户会直接跳过验证，那等于没有签名。

## 怎么核对一份发布

```sh
sh scripts/verify-release.sh dist          # 先验签名，再核校验和
```

顺序不能反：校验和只回答「文件与清单一致吗」，签名回答「这份清单是我们发的吗」。
先核校验和的话，一个替换了产物**并且**改了清单的发布会先通过那一步。
